## How to read this

- **recall@10** is the share of the exact top 10 (brute-force cosine search)
  that an index returns. 1.0 is perfect.
- **QPS** is one query per call from one caller thread, through each
  library's Python API. **batch QPS** sends all queries in one call.
- **Build** for SrvDB includes writing to disk and `persist()` (the data
  survives a crash). The other libraries build in memory only and save
  nothing. This is part of what SrvDB is for, and it costs time.
- **Peak RSS** is the whole process, including the dataset copy the runner
  holds, which is the same for every index.
- **1 thread** limits every library (and SrvDB's internal pool) to one
  thread. **All threads** lets each use every core.

SrvDB rows and lines are highlighted. The summary lists each index's
fastest setting that reaches recall@10 of at least {TARGET}, and says in
plain words where SrvDB is slower as well as where it is faster.

## Reproduce

Set up a separate venv for the competitors (they are never SrvDB
dependencies), build SrvDB into it, and run from a clean checkout:

```bash
uv venv -p 3.12 .bench-venv
uv pip install -p .bench-venv/bin/python -r benchmarks/compare/requirements.txt
VIRTUAL_ENV=$PWD/.bench-venv .bench-venv/bin/maturin develop --release
.bench-venv/bin/python benchmarks/compare/run.py --dims 384,768 --ns 5000,50000
```

The run rewrites `website/src/data/benchmarks/comparison.json`; rebuild the
site to update this page. Method details and licences of the compared
libraries are in `benchmarks/compare/README.md`; SrvDB's own per-mode
harness is described in `docs/benchmarks.md`.
